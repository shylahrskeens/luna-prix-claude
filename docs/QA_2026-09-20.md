# Luna Prix — QA pass, 2026-09-20

Browser QA against the running dev server at `http://localhost:5173/` (Chrome, macOS).
No source file was edited. Evidence images: `docs/evidence/qa-2026-09-20/`.

**Headline: no BLOCKERs found.** The end-of-race fix works — you always reach the results
screen, and a key press does shorten the wait. But the *total* wait is ~5.8 s, not ~4 s,
because a fixed 1.8 s delay sits after the tail and nothing skips it.

## BLOCKER

None found in what I covered. See "Not verified" for the gaps.

## SHOULD-FIX

### 1. Results screen arrives ~5.8 s after crossing the line, not ~4 s
- **Did:** Quick Race on Lunacia Canopy Run. Drove to the line, then measured the exact
  simulated time from the player crossing to `phase === 'complete'`, and the wall-clock
  time from `complete` to the results screen appearing.
- **Happened:**
  - tail (cross → complete) = **3.95 s** — the 4 s cap is working correctly.
  - complete → results screen = **1.88 s** (re-measured twice more: 1.805 s, ~1.8 s).
  - **Total cross → results ≈ 5.83 s.**
- **Expected:** results within ~5 s, per the brief. 5.83 s is over that bar.
- **Mechanism:** `src/main.ts` `finishRace()` ends with
  `window.setTimeout(() => { ... this.go('results', ...) }, 1800)`. That 1800 ms is real
  wall-clock time and is added *after* the 4 s tail, so the two stack.
- **Severity:** SHOULD-FIX. You are never actually stuck — the screen always arrives.

### 2. A key press skips the tail but cannot skip the last ~1.9 s
- **Did:** Crossed the line, let the tail arm for 0.5 s, then dispatched a fresh key
  (`KeyZ`) through the game's own keyboard path and measured again.
- **Happened:** the tail ended on the **very next frame — 0.05 s** after the press
  (total tail 0.55 s instead of 3.95 s). The skip works exactly as intended.
  But the 1.8 s `setTimeout` still runs afterwards, so press-to-results is still ~1.9 s.
- **Expected:** "any fresh key press or tap skips it" reads as skipping to the results.
- **Severity:** SHOULD-FIX — same root cause as #1. Making the 1800 ms timer cancellable
  by the same skip would fix both.

### 3. Home screen undersells the game: "two bonus events", but three ship
- **Did:** Read the home screen, then the Records screen.
- **Happened:** Home body copy says "...and **two** bonus events...", and the Bonus Events
  button subtitle reads "Mega Ramp and Gator Gauntlet". The Records screen lists **three**:
  Mega Ramp, **Luna Launch**, Gator Gauntlet. `src/data/bonus.ts` defines all three.
- **Expected:** the front page should name all three; Luna Launch is finished content that
  a judge may never find.
- **Severity:** SHOULD-FIX (front page, submission day).
- **Source:** `src/ui/screens.ts:154` and `:160`.

### 4. Time Trial results say "P1 — On the podium." for a field of one
- **Did:** Ran a Time Trial on Lunacia Canopy Run to completion.
- **Happened:** Results headline reads **"P1"** / "On the podium." with a one-row finishing
  order. Rewards correctly showed a flat "+40" and "Rating — Unaffected in this mode".
- **Expected:** the rewards code already treats a time trial as uncontested on purpose
  (the comment in `finishRace()` says finishing 1st there "means nothing"). The headline
  copy was not given the same treatment.
- **Severity:** SHOULD-FIX — it reads as a hollow win.
- **Screenshot:** `docs/evidence/qa-2026-09-20/results-timetrial.jpg`

## What passed

- **Cold load.** `DOMContentLoaded` 177 ms, `load` 345 ms, 46 requests. **Zero console
  errors and zero warnings** — the only console output was `[vite] connecting/connected`.
  Interactive home screen well under half a second.
- **Garage.** Axie pick (Buba/Puffy/Pomodoro) swaps the 3D model, stats, body-parts table
  and the "In the Moonshard" bars. Chassis pick (Dartwing/Moonshard/Terrapin) swaps the
  kart mesh. All four part slots present (Chassis, Engine, Tires, Suspension).
- **Buying a part.** Clicked Ember II → confirm dialog "Buy Ember II? 180 coins..." →
  Buy and fit. Coins went 230 → 50, the part showed FITTED, "Level 1/3" and an
  "Upgrade Ember II to level 2 — 140c" row appeared correctly greyed at 50 coins.
  Previously-affordable parts correctly dimmed afterwards.
- **Text audit.** Scripted scan of every leaf element on the garage screen for horizontal
  clipping and for `lorem/TODO/TBD/placeholder/undefined/NaN` found **none**. No
  misspellings spotted on home, garage, axie, track select, records or results.
- **Race HUD.** Countdown runs 3→0; position, LAP n/3, track name, lap timer, BEST,
  minimap, speed readout and the "DRIFT TO CHARGE" meter all render.
- **HUD speed is correct.** HUD read **174 km/h** at the moment internal speed was
  48 (m/s). 48 m/s = 172.8 km/h — the readout and its units check out.
  Screenshot: `docs/evidence/qa-2026-09-20/hud-pause-174kmh.jpg`
- **Driving.** Holding throttle then adding steer then drift, speed climbed
  26 → 38 → 48 m/s (94 → 137 → 173 km/h) over ~5 s. Off-track triggers a respawn.
- **Frame rate.** Steady **118–121 fps** across every real-time sample. No stutter or
  dropped frames observed while the tab was in the foreground.
- **Auto-pause.** Backgrounding the tab pauses the race (matches the `visibilitychange`
  handler in `main.ts`). Pause overlay offers Resume / Restart / Quit to menu; Restart
  put the race cleanly back to t=-3.
- **Results → Garage → race again.** Results shows rank, Time, Best lap, Top speed,
  Drifting, Boosts, a finishing-order table, per-lap splits and a Rewards panel.
  The "Garage" button returned to the garage with coins carried across (196). Ran
  7 races in the session back-to-back with no crash and no console error.

## Not verified (be aware before shipping)

1. **Narrow / phone width (~400 px) — NOT TESTED.** `resize_window` reported success but
   the viewport stayed 1307 px, and Chrome does not re-layout a background tab, so I could
   not measure it. For information only (read from source, *not* observed in a browser):
   `src/ui/styles.css` has breakpoints at 1100/900/620/560 px plus an
   `(orientation: portrait) and (max-height: 560px)` rule and a touch-control layer.
   Someone should open it on a real phone before submitting.
2. **Not exercised:** Ranked mode, Bonus Events, Multiplayer screen, the Ruin Reactor
   Rally and Cloudforge circuits, gamepad and touch input, audio.
3. **Drift-boost release** was not visually confirmed — the drift charge meter was covered
   by the pause overlay in the one screenshot I got of it. Speed did rise through the
   drift, but I did not see a boost fire.

## Notes on method (not defects)

- The dev server reloaded my tab at least three times mid-test because the repo was being
  edited during the pass. Two apparent "race ended with no results screen" readings were
  traced to those reloads (confirmed via `performance.timeOrigin`) and are **not** bugs.
- The automation harness swallows the first synthetic click after a navigation (verified:
  zero `pointerdown/mousedown/click` events reached the page). **Not** a game bug — when a
  click lands, the app responds immediately.
- Chrome halts `requestAnimationFrame` in a background tab, so the game freezes and reports
  0 fps there. Expected, and the game pauses itself anyway.
- Sustained driving was done by dispatching held `keydown`/`keyup` through the game's own
  input path, because the click/key tool only sends instantaneous presses which cannot hold
  a throttle. Timings above are wall-clock or simulated seconds as labelled; simulated time
  was verified to run 1:1 with wall time when the tab is visible (1.5 s sim in 1.502 s).
